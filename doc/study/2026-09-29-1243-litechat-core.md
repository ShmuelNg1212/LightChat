## Intended Outcome

An occasional user can access useful AI models without buying a recurring subscription. The defining product loop is: establish an account and available credit, understand model options and price, send a prompt, receive an answer, see the cost and remaining credit, and return to the saved conversation.

Proposed acceptance criteria, subject to the study checkpoint:

- A user signs in and sees only their own conversations and balance.
- They can choose between actual available models from at least two providers, if the supplied proxy permits it; unsupported models are never presented as working.
- A prompt and follow-up produce real answers that preserve conversation context. A chosen model is recorded per response, including when switched.
- Progress appears while waiting; streaming is preferred if verified supported. Errors and interrupted responses are understandable and do not silently appear complete.
- Conversations survive refresh and sign-in, can be renamed, revisited, and deleted through the app.
- The interface displays model pricing, per-response usage/cost, and remaining credit with an explicit currency or clearly labeled demo unit. Estimates are distinguished from settled charges.
- Insufficient credit prevents a paid request; rapid double clicks, retries, and concurrent tabs do not create duplicate debits or overspend available credit.
- A provider rejection leaves the user with an actionable error. An ambiguous upstream timeout is reconciled rather than automatically retried and potentially billed twice.
- The app works on a phone and desktop, with keyboard-accessible controls. The proxy credential never reaches browser code.
- Adding credit is demonstrable. Recommendation for the initial assessment: explicitly labeled demo/admin-issued credits; real paid top-ups remain a separate scope decision. A demo balance is not a claim of production payment support.

## Options & Tradeoffs

These are engineering judgments, not claims that one stack is universally better.

| Option | Pros | Cons | Effort | Risk |
| --- | --- | --- | --- | --- |
| Django monolith, templates, small JavaScript streaming client, PostgreSQL | Continuity with WhatsUp; standard auth/admin/ORM/testing conventions; one primary application | Streaming and synchronous transaction boundaries require care | Moderate | Low–moderate |
| Rails monolith with server-rendered UI | Matches article author's successful framework choice; strong conventions | Changes framework from user's inspected prior project without a demonstrated need | Moderate | Moderate |
| Separate SPA and API services | Independent frontend/backend development | More deployment, authentication, state, and contract decisions for this scope | Higher | Higher |

## Recommendation

Use a separate Django monolith with PostgreSQL, Django templates, framework session authentication, and a small browser client for response updates. Prefer a supported Django release; 5.2 documentation was consulted for feasibility, not an installed or locked version. Select and pin current compatible versions during planning. Use ASGI if streaming is supported. Django documents async views and advises isolating transactional work in synchronous functions when called from async code.

Keep accounts, conversations, provider access, and usage accounting as clear application responsibilities in one deployable service. Do not adopt microservices or a generalized agent framework for this brief.

Proposed data concepts: user; conversation; message; model/rate snapshot; generation attempt; wallet; append-only credit/debit/reservation ledger. A generation needs a stable request identifier and explicit pending, streaming, completed, failed, or reconciliation-needed status. These are architecture recommendations, not a finalized schema or implementation checklist.

The browser submits to our server; our server validates ownership and budget, calls the approved proxy with the server-held key, relays the verified response format, persists the conversation, and settles usage once. Monetary amounts use precise decimal or integer subunits, not binary floating-point arithmetic. Retain pricing snapshots so historical charges do not change with future prices.

Reserve a verified upper bound before dispatch and settle against authoritative usage afterward. Short database transactions protect balances; do not hold a transaction open for an entire generation. If the proxy cannot provide reliable usage or a defensible spending cap, resolve that limitation before claiming accurate prepaid billing. Aborted or incomplete requests can still incur provider charges; missing final usage must enter reconciliation rather than being assumed free. Keep the upstream account's credits distinct from each app user's wallet.

Prioritize text chat, model choice, private saved history, and credible metering. Attachments and web search are confirmed advertised Litechat features, but recommended as a later increment unless the user's assessment requires them. This scope choice must be acknowledged at the review checkpoint. Do not render inert controls implying unsupported capabilities.

## Risks & Open Questions

- **Product boundary:** recommendation is a new application; WhatsUp remains a reference. Confirm if the intention was instead to add this to WhatsUp.
- **Billing scope:** should the initial assessment use clearly labeled demo credits or actual payment-backed top-ups? Recommend demo credits until commercial payment scope is explicitly required.
- **Feature scope:** recommendation defers attachments and web search, while recognizing they exist on the reference landing page.
- **Reliability:** duplicates, simultaneous spending, partial streams, rate limits, upstream timeouts, and process restarts require observable outcomes and accounting tests.
- **Privacy:** ownership checks on every conversation/message endpoint; secret redaction; sanitized generated Markdown; no broad logging of prompts or credentials.
- **Cost:** verified token/usage units and rates are essential; tool, cached-token, or non-text fees must not be silently ignored when enabled.
- **Evidence gap:** current signed-in UX and API behavior have not been observed. Those gaps limit fidelity claims and integration estimates.
- **Delivery:** no deadline, hosting budget, or target was supplied; no completion-time estimate is justified yet.

### New evidence at review

The proxy was reachable from this machine and publishes documentation at <https://proxy.litechat.ai/docs> ("BUILD LLM Proxy", revision 2026-09-19). The Overview, OpenAI Chat Completions, OpenAI Responses and Anthropic Messages pages were read. The Google Gemini page timed out on every attempt and remains unread. No key was used and no paid request was made.

| Previously unverified | Now established (documented, not yet sample-verified) |
|---|---|
| API protocol | Three provider-style interfaces with one model each: OpenAI (`/openai/v1`, `gpt-5.6-luna`), Anthropic (`/anthropic/v1/messages`, `claude-haiku-4-5-20251001`), Google (`/google`, `gemini-3.8-flash`). |
| Credentials | One key per provider, not one proxy key. OpenAI uses `Authorization: Bearer`, Anthropic `x-api-key`, Google `x-goog-api-key`. |
| Actual models | **All three interfaces are served by DeepSeek Flash** and "do not reproduce the named providers' model behavior." |
| Streaming | Documented for OpenAI Chat, OpenAI Responses and Anthropic Messages, each with its own terminal-event check. OpenAI Chat needs `stream_options.include_usage` to receive usage in a stream. |
| Usage | Token counts are returned in each provider's format. |
| Prices, currency, rate limits | **Not published.** 429 exists, with no numbers. |
| Errors | 400; 401/403; 429 (bounded delay); 502/504 (upstream failed); 503 (contact admin). "Do not automatically retry after partial output arrives." "Usage can be unknown after a failure." |
| Spending cap | `max_tokens` / `max_output_tokens` bounds the output of every request. |
| Conversation state | The app keeps and resends the full history. Responses API: `store` and `previous_response_id` are unsupported. |
| Attachments | Images and provider file APIs exist; files expire after one hour. |

### Consequences for the recommendation

1. "Multiple providers" means three provider interfaces over one underlying model. The UI must say so plainly; presenting them as genuine GPT, Claude or Gemini would violate the acceptance criterion on honest model presentation.
2. Because the proxy publishes no prices, the app defines its own **demo rate table** in a labeled demo credit unit. This makes demo credits the only truthful option, not just the cautious one.
3. The reservation bound is achievable: a conservative input-token bound plus the request's output-token cap, priced at the snapshot rate.
4. The study's single `LITECHAT_API_KEY` becomes three keys (see the plan).
5. Stack versions were checked against PyPI during planning. WhatsUp pins Django 6.1.1 with `django-environ`, `dj-database-url` and a SQLite fallback locally. The plan follows that precedent in place of the study's Django 5.2 / ASGI suggestion; the plan explains why.
6. The documentation-only `outputs/litechat/` folder mentioned in Current State does not exist in this workspace. This repository (`/Users/shm/litechat_midterm`) is the project from here on.
