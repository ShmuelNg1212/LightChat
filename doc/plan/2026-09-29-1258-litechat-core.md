## Technical approach

Stack decisions are the Vine's to make. They're summarized here so the reasoning is on record.

- **Stack, following WhatsUp's pinned precedent:** Python 3.14 (installed at `/opt/homebrew`), Django **6.1.1**, `django-environ` 0.14.0, `dj-database-url` 3.1.2 (SQLite locally; PostgreSQL through `DATABASE_URL`), `httpx` 0.28.1, `markdown-it-py` 4.2.0, `nh3` 0.3.7. Everything is pinned in `requirements.txt` and installed into a `.venv` with pip. Tests use Django's own test runner.
- **Sync (WSGI) streaming, not ASGI:** a sync view returns `StreamingHttpResponse` over a generator that reads the upstream stream with `httpx`. Each short database step runs in its own `transaction.atomic()` block, and no transaction stays open during a generation. This avoids the async/transaction pitfalls the study flagged. The cost is one server thread per active stream, which is acceptable at this scale.
- **`httpx`, not the provider SDKs:** the official SDKs retry automatically by default, and the proxy docs forbid retrying after partial output. Calling the documented HTTP endpoints directly gives exact control over timeouts, retries and usage parsing, and uses a single dependency. A small SSE line parser (about 30 lines, unit-tested) handles stream framing.
- **Money:** integer **micro-credits** (1 credit = 1,000,000 µcr); no floats anywhere. Each `Wallet` has `balance` and `held`, and available = balance − held. Every change runs as a single conditional `UPDATE … WHERE balance − held >= amount` inside `atomic()`. This is race-safe on both SQLite and PostgreSQL without a long-held lock. Every change also writes an append-only `LedgerEntry` (grant, top-up, hold, release, charge, adjustment) with the balance after it.
- **Reservation:** hold = ⌈input bound × input rate⌉ + ⌈`max_output_tokens` × output rate⌉. The input bound is the UTF-8 byte count of the full request plus 16 per message, because a token is never shorter than one byte. Settlement charges the actual usage at the **rate snapshot** stored on the generation and releases the rest. If usage ever exceeds the hold, the charge still applies and the generation is flagged `overage`.
- **Generation lifecycle:** `pending → streaming → completed | truncated | failed | interrupted | needs_reconciliation`.
  - A 400, 401/403 or 429 before any output means nothing was generated, so the hold is released.
  - A 502, 504, timeout, disconnect, or stop without final usage leads to `needs_reconciliation`. The hold stays until an admin resolves it.
  - Nothing is retried automatically.
- **Duplicates and concurrency:** the browser sends a fresh `client_request_id` (UUID) with each submit, and it is unique per user. A repeated ID returns the existing generation instead of dispatching again. There is at most one active generation per conversation and three per user.
- **Browser protocol:** `POST /c/<id>/send` streams newline-delimited JSON events (`delta`, `done` with sanitized HTML, cost and balance, `error`). A small vanilla-JS file reads them with `fetch` and a `ReadableStream`. There are no front-end frameworks.
- **Privacy:** every conversation query is filtered by `owner=request.user`, so another user's IDs return 404. Keys are read only in the proxy client. Logs record generation IDs and statuses, never prompt text or headers. Markdown is rendered with raw HTML disabled, then sanitized with `nh3`.
